# The item catalogue

Two files, one direction:

| File | Decides | Edit it when |
| --- | --- | --- |
| `tools/items/catalogue.py` | WHAT exists: ids, names, slots, tiers, sets, unique effects, sources, planned recipes | adding or removing an item |
| `tools/gen_items.py` | the NUMBERS and the WORDS: stat budget, weapon damage, prices, descriptions, shop shelves, gear pools | retuning, rewording, restocking |

`python tools/gen_items.py` writes everything; `python tools/gen_items.py --check` exits 1 if anything
would change. Never edit a file that starts with `; Generated by tools/gen_items.py`: the next run
overwrites it.

## Add an item

1. Add its entry to `ITEMS` in `catalogue.py` (the grid loops, a set's `pieces_spec`, `LEGENDARIES`,
   `_potion(...)`, `_mat(...)`). Never rename or reuse an id; ids are in saves.
2. If it is not grid gear, give it a line in `NAMED_TEXT` in `gen_items.py`. Grid gear is described
   from `PIECE_TEXT` (what the piece is) and `MATERIAL_TEXT` (what it is made of). No em-dashes, and
   the fifth realm is never named.
3. An equippable needs nothing else: its stats come from `stat_block`, its price from `item_value`
   and, for a main-hand item, its weapon from `weapon_tres`. To give it stats of its own, add an
   allocation to `ALLOC_OVERRIDE` (the first stat is the primary and absorbs rounding).
4. A consumable needs a price in `CONSUMABLE_VALUE`; a new material one in `MATERIAL_VALUE`.
5. Give it somewhere to come from: a row in `SHOP_STOCK`, a tier in `POOLS`, or a loot table, recipe,
   quest or boss reward authored elsewhere. `--validate` fails an equippable with no source.
6. Run `python tools/gen_items.py`, then `--check`, then the filtered tests:
   `dotnet test tests/Embervale.Tests --filter "FullyQualifiedName~ItemCatalogueTests"`.

## The budget

`budget_points(item_level, slot, two_handed, rarity)` is what an equippable may spend, in points
(one point is one Armor). `STAT_WEIGHT` prices every other stat. `weapon_damage` and `item_value`
are the other two authorities. All four are mirrored in C# by `ItemBudget`
(`src/Debugging/ItemValidator.Content.cs`); change both sides together, or `ItemCatalogueTests`
fails. `--validate` allows a quarter either way so a hand-tuned item is legal and a typo is not.

## What the generator touches that it does not own

- The 12 `EXISTING_RETROFIT` items: only `ItemLevel`, `Tier`, `TwoHanded`, `WeaponClass` and
  `ArmorWeight` lines are appended. Nothing else in a hand-authored item is rewritten.
- `data/shops/*.tres` and the three gear pools in `data/loot/`: only sub-resources whose id contains
  `_ics_` and their entries in the `Stock` / `Entries` list. Hand-authored rows are left alone.
- `data/locale/strings.csv`: only the `ics:content` block.
- `src/Debugging/ItemValidator.Content.cs`: only the id lists between the `generated` markers.

## Conventions other systems rely on

- A recipe scroll `item.recipe_scroll.<leaf>` teaches `recipe.<leaf>` (`ItemCatalogueIds.RecipeOfScroll`).
- A unique effect's description in the locale has its numbers already filled in; it has no placeholders.
- A healing consumable carries `Magnitude`, not the legacy `HealAmount`.
- Player weapons live in `data/weapons/Player<Item>.tres`, one per main-hand item.
